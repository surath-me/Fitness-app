# Coach: personal training and food tracker

A single-file web app for one person (Surath). It tracks meals and macros, lift weights, and plans each day's workout, carrying missed sessions forward. It is hosted as a static site on Vercel from this repo, with one small serverless function for optional cloud backup. There is no build step and no framework.

## Files

- `index.html`: the whole app (HTML, CSS, JavaScript). Vercel serves it from the repo root.
- `apple-touch-icon.png` (180), `icon-192.png`, `icon-512.png`, `favicon-32.png`: the app icon (blue gradient, glass dumbbell). Must sit next to `index.html`.
- `manifest.webmanifest`: name, standalone display, icons.
- `apple-touch-icon-dev.png`, `icon-192-dev.png`, `icon-512-dev.png`, `favicon-32-dev.png`, `manifest-dev.webmanifest`: the dev copy's icon (the same dumbbell on orange, with DEV under it) and name, Coach Dev. A small script at the top of `index.html` switches to them on every address except the live ones (`fitness-app-chi-gilt`, `fitness-app-surath-me` and `fitness-app-git-main-surath-me` on vercel.app), so the dev site, previews and this Mac's test servers never look like the real app. Add a new live address (a custom domain) to that list.
- `api/sync.js`: the cloud backup function (Vercel Node function, no npm packages, Node built-ins and `fetch` only). It stores the app's data in Upstash Redis.
- `api/chat.js`: Coach chat (beta), the same kind of function: one continuous conversation with Claude, stored next to the backup.
- `vercel.json`: runs the function in Frankfurt (`fra1`), next to the database.
- `.gitignore`: keeps the local `.vercel` link out of git.
- `CLAUDE.md`: this file.

## How to work on it

- Edit `index.html` directly. Keep it one file, vanilla JavaScript, no dependencies, no CDN links, no web fonts. `api/sync.js` also stays dependency-free.
- Deploy by pushing to `main`. Vercel redeploys on its own. No build command, no framework preset.
- Most requests are small edits to the config block at the top of the script (foods, lifts, sessions, targets). Do those first and leave everything else alone.
- After a change, open the page and check each tab (Train, Eat, Progress, Settings) for console errors.
- **Always pull up the local preview after a change** so Surath can try it right away: start `coach` from `.claude/launch.json` (it opens http://127.0.0.1:4173, a clean copy started on 28 Oct 2026; the older copy at localhost:4173 only holds leftover test taps), set the Browser pane tab to light mode, reload it and leave it on the screen that changed. Do this before asking whether to push.
- Keep the version in `APP_VERSION` up to date when behaviour changes. The installed app checks it when it comes back to the foreground (`checkVersion` fetches `/`) and reloads itself when it differs, unless a rest is counting down, a sheet is open or a field has focus, so a push reaches the phone without closing the app.

## Design rules

- **Light and dark follow the system** (`prefers-color-scheme`), with no switch in the app. Every colour is a token in `:root`, and the dark block below it sets Apple's iOS 26 dark values (black background, `#1C1C1E` cards, `#2C2C2E` cards inside sheets, blue `#0091FF`). Never hard-code a colour in a rule; add a token with both values. White stays white only for text on coloured fills, the switch knob and the touch glow. `theme-color` has a light and a dark entry for the status bar.
- **iOS 26 Liquid Glass, following Apple's HIG.** The `.glass` class is the material: translucent white tint, backdrop blur, saturation and brightness, a specular highlight and touch glow (`::before`) and a light rim (`::after`). Safari cannot do real lensing (no SVG filters in `backdrop-filter`), so edges and inner light imply it.
- **Glass is for the navigation layer only**: tab bar, its accessory (rest timer), toolbar buttons, menus, sheets, alerts and toasts. Content (cards, rows, the week strip) stays solid. No glass on glass. Surath wants the glass fairly see-through (light tint, 7 px blur for bars and buttons) so the content behind shows; small glass is clearer, large glass (menus, sheets) is thicker but still lets the page through. Tint glass only for the primary action (`.btn`, prominent glass). In dark mode the glass follows Apple Fitness's tab bar: a mid grey at the same opacity, faint white highlights (`--spec`, `--rim`), and a tab selection darker than the bar (`--tab-sel`), not lighter.
- **Glass materialises, it does not fade.** Appearing and disappearing ramp blur, tint and scale (`.ghost` state and the `mat` animation). Only what sits on the glass fades.
- **Interaction:** touching glass lights it from the fingertip (`.lit`, `--px`/`--py`) and it grows slightly with a spring. Controls lift into a see-through lens while touched: the tab bar selection (drag it across tabs), segmented control thumbs (drag them), and switch knobs.
- **The end of a page** stops about 20 px above the tab bar, or above the rest timer while it shows (`.app` bottom padding follows the dock's own bottom; every page's last block has the same 16 px margin). Surath found the old 150 px too much.
- **Native patterns in place:** a transparent nav bar with glass toolbar buttons (`toolbarHTML`: a glass Back button on Settings pages, separate `+` and `⋯` glass buttons on the right, not one shared capsule; Today is a tinted capsule beside the week arrows, not in the nav bar), large titles that hand over to an inline title and subtitle on scroll, a soft scroll edge effect at the top only (`.edge.top`; Surath does not want a fade at the bottom), a floating tab bar that always stays full size (Surath does not want it minimising on scroll), the rest timer as a tab bar accessory above it, menus that grow out of their button and shrink back onto it (`openMenu`, `closeMenu`: moved and scaled from the top left corner onto the button's exact box, never scaled around a point, which landed them off the button; in the last moment of closing the button fades in under the fading menu; an open menu freezes the page, so a tap outside closes it and only then does the page scroll, `freezeForMenu`; a menu opened from the page is placed in the page, one from the nav bar or a sheet stays on screen), sheets that always slide up from the bottom (Surath does not want them zooming out of the `+`) and are inset glass at partial height but edge to edge and opaque when tall (`.sheet.full`), a sheet bar with Close or Back leading and an inline title, a glass alert (`askGlass`), inset grouped cards, swipe left to delete with Undo, on meal entries, on lifts added by hand or offered under If you have time (a planned lift never swipes away: its swipe marks it as not done instead) and on each set of an opened lift (iOS 26 style: rows run edge to edge with only the separator inset (`.swipe::after`); every separator in a card is inset 16 px on both sides and 1 px thick, like iOS 26 Health (`--sep`, `--sep-w`: #E7E7E8 on white in light, a dark grey about 20 levels above the card in dark), so a swiped row slides off the card's left edge; the touch highlight and the swiped row are the same grey rounded rectangle inset from the card by the same 6 px on every side, with 18 px corners everywhere (`--hl-gap`, `--hl-r`, `--hl-outer`), set by eye: Surath wanted to see it this way rather than by the rule that the inner radius is the card's radius less the gap (26 - 6 would be 20). Every other press highlight is a pill, fully rounded and inset from its card (Settings rows `.srow::after`, menu items `.menu .mi`, which are compact: 38 px rows, 14 px labels, 11.5 px helper text, below the usual 44 px because Surath found 46 px and 15 px too big, the food and exercise list rows `.food::after`, the Add food line `.addline::after`). He tried a 3 px by 6 px inset with 16 px corners (uneven), a 6 px gap with 20 px corners and with 12 px ones, 22 px with a 4 px gap, 21 px with a 5 px gap, a 6 px gap with 22 px corners, 21 px, then 18 px (`.swipe-fg::before`, `.ex-head::before`, `--swipe-row`); the action is a red capsule with a trash icon, no word, inset 8 px from the row and 10 px from the edge, that starts as a circle and stretches as the swipe goes on while the icon springs in (`--ps`), bumping past 40%; short of halfway closes, past halfway or a flick opens at 82 px, past 40% of the row deletes on release (Surath found 60% too far), swiping right does nothing, scrolling or tapping elsewhere closes; `setSwipe`, `DEL_W`. On an exercise only the head swipes; each set row swipes on its own (`.setswipe`, `removeSet`), and the last set left has no delete), tap-to-complete sets, banner toasts, all low, just above the tab bar, the rest timer or the keyboard (Surath): a green tick when something worked, a red skip mark for a skipped or not done session, a red cross when something failed or is missing (`toast(m, { err:true })`; the top is out of reach). On Train the session card shows only its first reason (no Why this plan; Left out today already says what was held back and why), and Added has the same heading and note style as Left out today. The keyboard always covers the page, as in a native app: while it is up (`kbopen` on `html`: the visual viewport is over 120 px shorter than `innerHeight`), the dock with the tab bar and rest timer slides down behind it, by `--vvt` more when iOS shifts the visible area up for a field near the end of the page (that shift once hid the keyboard from the check and left the tab bar riding on the keyboard). Partial sheets sit above the on-screen keyboard (`--kb` from `visualViewport`); full-height sheets run to the bottom of the screen with the keyboard over them and take `--kb` as bottom padding, because stopping them at the keyboard left the page showing around iOS 26's floating keyboard. Full-height sheets (the food list and Quick entry always, so switching between them never moves the tray; Quick entry opens in its name field with the keyboard up, `focusQuick`, called inside the tap so iOS shows the keyboard) have a fixed top so short lists stay under their search field.
- **A day with nothing to train** shows one card in the style of Apple Fitness tips instead of the session ring (`restCard`): a grey icon on the left (moon with z's), a bold title, one grey line of text, and a full-width tinted button (`.btn.soft`: accent at low opacity with `--accent-ink` text, like Fitness's Get Started). Rest day offers Choose a session, or, when a session was missed earlier that week and this rest day can take its place, Train it today (`swaprest`). A skipped or missed session is not a good thing, so it shows in red: a red skip-forward icon in a filled circle (`ICON.missed`, `.restcard.bad`; Surath did not like an ✕), a red dot in the week strip (`.dots b.x`) and a red mark on the Session skipped toast. A skip while a rest day is still free that week offers Rest today instead (Bring it back stays in ⋯); with no rest day left it offers Bring it back. A recovery day explains the hold, a past rest day is calm, and past days have no button.
- **The app never zooms:** no pinch and no double-tap zoom (viewport `maximum-scale=1, user-scalable=no`, `touch-action:pan-x pan-y` on `html`, and Safari's `gesturestart`/`gesturechange` cancelled, because Safari ignores the viewport setting). This also stops Safari zooming into a field when it gets focus.
- **Settings (the `setup` tab in code; Surath renamed it from Setup) follows the Apple Health profile:** a centred header (app icon, name, last backup with Back up now), then inset grouped rows with chevrons under bold section headers. Each row opens its own page (`ui.setupPage`, `SETUP_PAGES`, `setupPage`) with a glass Back button and an inline title. Back also works by swiping from the left edge or tapping the Settings tab. Value pickers are native `<select>` styled as the iOS menu picker (`.pick`), so the phone shows Safari's own picker.
- **A day is either a training day or a rest day, never both, and Train decides it** (`dayType`): a day with a session (planned, chosen or trained) eats as a training day; a rest day, a skipped session or a missed one eats as a rest day. Eat has no way to pick it (Surath removed the picker: it should come straight from Train), and a type saved by the old picker (`days[date].type`) is ignored.
- **Hierarchy in lists:** on Eat, each meal's name and totals are the headline (17 px name, 16 px bold black totals); a detail in a food's name ("Tandoori chicken (edible meat)", or after a comma in a food that is not one of the app's own, which keep names like "Egg, whole") sits on the grey line with the amount (`nameParts`, also used by Coach AI's cards); each food's own macros are small, regular and grey, and an empty meal shows no row of zeros. On Train, a closed exercise shows the weight to load big on the left (Surath likes it there, it is the number that matters at the gym), the lift's name with the reps needed under it (`3 × 8–12 reps`, `reps/side` for single-arm lifts; he wants those at a glance) and the status chip, nothing else; the reasoning and what was logged (`exWhy`) appear only once it is opened, above the sets.
- **Logging lifts:** a set counts as done only when its tick is pressed (`d:true` on the set, `isDoneSet`; older sets without `d` count once they have reps). Typing numbers never logs a set. Only one exercise is open at a time (`closeEx`). Hold an exercise for about half a second, then drag it to reorder; the order is saved per day (`wk.order`, `byOrder`). Lifts added by hand on top of the plan sit under an Added heading (`plan.added`, from `wk.added`) and do not count towards the session ring or time. That includes a planned lift the day left out (time or recovery) and then added through +, and they stay there once logged and on past days. Add an exercise has a search field (`exListHTML`). There is no Add set or Remove last (Surath does not use them): a set is deleted by swiping it left, and a lift's set count follows its rows once it has any (`setTarget`). A set logged with **0 reps** is valid: it counts as done and shows a grey dot instead of the tick (`.check.zero`), and it never counts as the weight lifted, on the lift, in progression or on Progress (`topW`). Typing 0 in reps logs it at once with no rest timer (the one exception to typing never logging a set); changing the 0 to more reps needs the tick again, and tapping the dot clears the 0. **Not done** is the swipe action of a planned lift on today or a past day (`swipeAction`, `notdone`, `wk.notDone`; Surath did not like it as a line inside the opened lift; there are no help notes under the lists on Train or Eat, he does not want them): a short swipe shows a grey capsule with the skip icon, a full swipe marks it and the row springs back instead of closing up. The lift gets a red Not done chip and has Undo. It still counts in the session ring, so its share of the session is lost (Surath chose not to do it, so the session cannot reach 100%); the same swipe then brings it back (a blue capsule), and ticking a set clears it. Future days and finished lifts have no swipe action. The next training day offers it under If you have time. Swiping an added lift left deletes it from that day (`removeLift`; a lift under If you have time goes to `wk.removed`), asks first if sets were logged, and has Undo. Planned lifts cannot be deleted, only marked as not done.
- **Rest timer** (`startRest`, `tickRest`): when the rest is over the accessory turns green with a full ring, pulses until touched, reads Rest over and Next set with a small negative timer of how long ago it ended (`#timero`), and stays until Done or a swipe down slides it away (`hideRest(true)`). Done after the rest stops the green pulse and shrinks and fades the whole timer from its current size (Surath found the dematerialise with the green edge odd there); Skip during the countdown dematerialises as usual. It never hides on its own, and while it is still counting down it cannot be swiped away.

## Data and storage

- Everything lives in `localStorage` under the key `coach-v1`, as one JSON object `S`. The device is always the source of truth and the app works offline. Settings has Export and Import for backups.
- **Cloud backup (optional, Settings, Your data, Cloud backup).** Each device connects once with a passphrase. `saveState` saves locally (`saveLocal`) and schedules a sync 4 s later (`scheduleSync`); the app also syncs when it opens, comes back to the foreground and comes back online (`syncNow`). The device keeps its sync details in `coach-sync` (passphrase, cloud revision, status) and the last synced copy in `coach-sync-base`.
- When both the device and the cloud changed, `merge3` merges them against that last synced copy, date by date: a day changed on one side takes that side (deletions included); a day changed on both sides combines food entries by id and keeps an entry identical in name, meal, amount and macros only once (every install creates the same starter days with different ids), real logged food beats an imported day total for the same day, the lift with more done sets wins, and the higher water wins. Custom foods are matched by name, unit and macros. On first connect there is no base, so both sides are combined and nothing is replaced. Erase everything turns sync off on that device first, so it never wipes the cloud.
- The function (`api/sync.js`) checks `Authorization: Bearer <COACH_TOKEN>`, keeps a revision number and answers 409 with the newer copy when a device is behind. Redis keys start with `COACH_PREFIX` (default `coach`, the live data; the dev site uses `dev`), like the chat's: `coach:meta` (rev, savedAt, device), `coach:state` and one `coach:snap:YYYY-MM-DD` per day kept for 31 days, all gzipped. `GET /api/sync?snapshots=1` lists snapshots and `?snapshot=DAY` returns one.
- Vercel setup: project `fitness-app` under `surath-me`, Upstash for Redis resource `coach-sync` (Free plan, Frankfurt, auto-upgrade and eviction off, so it can never cost money), env vars `KV_REST_API_URL` and `KV_REST_API_TOKEN` from the integration, and `COACH_TOKEN` (sensitive, production). The passphrase is in `data/cloud-passphrase.txt` on Surath's Mac only. Never print it, commit it or put it in a URL.
- **Dev and production share the one free Upstash database** (the free plan allows only one), walled apart by an Upstash ACL user `dev` (created 1 Nov 2026): it can only touch `dev:*` keys, with FLUSHDB, FLUSHALL, KEYS and the ACL commands refused, so the dev site cannot read, change or wipe the live `coach:*` data even if the code got the prefix wrong (checked with its token: real keys answer NOPERM, a transaction with one real key is thrown out whole; it can still list key names with SCAN, not their contents). Its REST token is in `data/upstash-dev-token.txt` on Surath's Mac only; never print or commit it. Vercel's settings (since 1 Nov 2026): Production and Development keep the main `KV_REST_API_TOKEN`, `KV_REST_API_READ_ONLY_TOKEN`, `KV_URL` and `REDIS_URL`; Preview (every branch preview, the dev site included) has none of them, only `KV_REST_API_URL`, the dev token as its `KV_REST_API_TOKEN` (sensitive), `COACH_PREFIX=dev` and its own `COACH_TOKEN` (sensitive; the dev passphrase is in `data/dev-passphrase.txt` on Surath's Mac). Vercel's login on previews is off, so the dev site opens on the phone; the passphrase guards the data. Careful: `vercel env rm NAME preview` deletes a variable from every environment when it is shared between several (it once removed `KV_URL` from Production); change a variable's environments through the Vercel API instead (PATCH its `target`). If the code starts using a Redis command outside reading, writing, keyspace and transactions, the `dev` user needs it added (`ACL SETUSER dev +command` with the main token).
- Import also takes a history file (`kind: 'coach-history'`, built from the chat logs). It only fills gaps (`mergeHistory`): a food day is added only if nothing is logged that day, a lift session only if that lift has no sets that day, and nothing is overwritten. A normal backup still replaces everything.
- Personal exports and history files live in `data/`, which is excluded from git (the repo is public). Never commit them.
- **Coach chat storage (`api/chat.js`):** keys start with `COACH_PREFIX` (default `coach`; a test deployment uses another): `:chat:meta` (months, seq), `:chat:m:YYYY-MM` (that month's messages, gzipped: `{n, role, text, ts, qid?, cut?, refused?, actions?}`, each action `{id, name, input, done?, ref?}`), `:chat:profile` (`{text, updatedAt, src?}`), `:chat:spend:DAY` (kept 3 days; the day is Stuttgart's, so the €1 starts again at local midnight, and a reply that fails part way still counts what it used), `:chat:busy` (a lock held while a reply or a clear is written, gone after 5 minutes at most: a second send at the same time gets 409 busy instead of two writers overwriting each other's month; it is released before the response ends, because work after the response is not guaranteed to run on Vercel), `:chat:reading` (the same, while imported history is read). Every question carries an id from the app (`qid`, stored with it): the same id again, from Try again or from a send the phone never heard back from, answers the stored question instead of storing it twice (older messages without an id match by text with `retry`); a reply cut off makes way, and one that arrived after all is just returned. A reply is kept only as Claude ended it: empty, it is not stored (it would go back empty with every later request, which the API refuses) and the app offers Try again; declined, even part way, what was written is dropped (as the API says) and the question is marked `refused` and left out of later requests, where it would only be declined again; any other ending than `end_turn` is stored as `cut`. The import (`distill`, effort medium, 16,000 tokens because thinking counts) keeps only a profile that ended on its own, returns the profile already written from the same history (`src`, a hash) without a second charge, and reads one at a time. Two providers (`AI`, `provider()`): Claude (`claude-sonnet-5-5`) when `ANTHROPIC_API_KEY` is set, otherwise OpenAI (`gpt-6.1-sol`, Responses API, `store: false`) when `OPENAI_API_KEY` is; `CHAT_PROVIDER=openai` picks OpenAI when both are, and `CHAT_MODEL` swaps the model within the provider (the prices stay the default model's). The request is written once (`buildRequest`: `{system, turns, now, effort, max}`) and put into each format (`claudeBody`, `openaiBody`); both streams come back in Claude's terms (`streamAI`: text, usage with cache reads and writes, stop `end_turn`/`max_tokens`/`refusal`), so everything after is shared. Claude: effort low, `fallbacks: "default"`, the instructions and profile a cached system prompt with a second cache mark on the last earlier turn. OpenAI: the same as `instructions`, reasoning effort low, and it caches the prefix on its own (writes 1.25 times input, prompts over 272k tokens at the long rates). The last 40 messages follow as plain text (the model's thinking is never stored or replayed, so the history can't break the thinking-block check), and the app data rides only on the new message. Real requests stop for the day at `CHAT_DAILY_CAP_EUR` (1 €), tracked from each reply's usage at the provider's prices (`costUsd`); GET returns the model's name and prices (`ai`), which Settings shows (Replies come from …) and the import estimate uses. Out of API credit (OpenAI's `insufficient_quota`, Anthropic's credit balance message) says so. The keyboard: iOS centres a newly focused field in what the keyboard leaves, so the message field at the bottom made it slide the whole screen up (a short conversation went out of sight and came back). A tap on the field is handled on touchend: the field takes the focus lifted near the top and see-through with a copy in its place (`liftField`, `dropField`), so iOS does not slide; the field then rides up with the keyboard on the measured keyboard curve (`KB_MS`, `KB_EASE`, a cubic-bezier so Safari runs it on the compositor; `KB_UP`, `KB_DOWN`), the conversation goes up only as far as its end has to, and the real layout replaces the moves after the slide. Going down is the same in reverse from the blur. Profile suggestions: when Coach AI learns something lasting it ends its reply with a `⊕ ` line (the instructions ask for it); the app shows it as a quiet Remember row under the reply (`chatMemsHTML`, `H.chatremember`), and one tap appends it to the profile as a `- ` line. Nothing is saved without the tap; a line already in the profile shows as Added. `/remember` gets a pretend one. Without either key every reply is a pretend one, streamed the same way (`/long` and `/error` test those cases). The server finishes and saves a reply even if the app closes mid-stream.
- Safari and an installed home-screen icon have separate storage. Say so if the user switches.
- `S` holds: `days[date].entries`, `workouts[date].ex[liftId] = [{w, r, d}]` (plus `added`, `removed`, `order`, `notDone` and `budget` per day), `dismissed` (skipped sessions), `rest` (rest day moves: `rest[date]` true or false overrides the split for that day), `assign` (a session chosen for a day, and past days pinned to theirs), `foods` (custom foods), `waist`, `water`, and `settings` (targets, caps, schedule, `returning`, `exCfg`, `planStart`).
- Dates are local `YYYY-MM-DD` strings. Weekday 0 is Sunday.
- `window.__TODAY__` overrides today's date for testing, `window.__LAUNCH__` plays the launch animation outside the home-screen app. `window.__coach` exposes internals for debugging.
- **Saved settings beat code defaults.** Changing `DEFAULT_TARGETS`, `DEFAULT_CAPS` or `DEFAULT_SCHEDULE` only affects new installs. To change values for the existing user, add a migration in `migrate()` or tell them to edit Settings.
- Foods, lifts and sessions come from code, so edits to `FOODS`, `EX` and `TEMPLATES` apply immediately. Per-lift overrides saved in `exCfg` still win.
- Seed data is only written on first run, never to an existing install.
- Food entries store their own macros, so editing a food never rewrites history.

## Planner rules (`buildPlan`)

- **The week:** the split's sessions (`settings.schedule`, Monday first) fill the week's training days in order (`weekPlan`, `sessionOn`). A day with a chosen session (`S.assign`, from Train a different session, or It was a training day on a past rest day) trains that one; every other training day takes the next session not done yet that week, and from today on also skips a session chosen for a later day, so the week still covers all five. A training day with no session left over is a rest day too: giving a past rest day a session frees a rest day, which lands at the end of the week and can be moved like any other. Changes never re-plan days already lived (`pinPast` pins past training days to their session first). Example: Monday and Tuesday rest, Tuesday was really Pull: Tuesday Pull, Wednesday Upper, Thursday Arms, Friday Push, Saturday Lower, Sunday free rest. The split's off days are the default rest days (Tuesday and Thursday). Surath can move a rest day within the week from ⋯ on Train (`canSwapRest`, `swapRest`): rest today instead of Thursday, or train on a rest day and rest on another day. The sessions after the moved day shift, so the week still covers all five (rest on Wednesday instead of Thursday and Thursday gets Wednesday's session). A week never has more rest days than the split (two): a move is a swap, and days already left behind are never used for it. A move is only offered when the rest day that moves is today or later (a past rest day was used and cannot be pulled forward; with Monday and Wednesday rested, Friday can only be skipped), neither day has anything logged and no day between them was trained. Each option says which days get which session (`swapEffects`). Moves have Undo.
- **Skipped and missed:** when no rest day is left to move, the only way out is Skip (`S.dismissed`). A training day that passes with nothing logged counts as missed (`missedDay`). Neither shifts the week. Their lifts, minus those in the next session, held for recovery or done since, show on the next training day at the bottom under "If you have time" (`makeUp`, `plan.extras`); after a day that was trained, the lifts marked as not done show there instead (`extras.notDone`), quieter than the day's own lifts and not counted in the session ring. As soon as one set of one of them is logged (a tick or 0 reps) it moves under Added, not into the session (Surath: logging a set means it is being done, however much of it): it goes into `wk.added` (`extraDone`), so it stays there when sets are unticked and on past days, and does not count in the ring. `relocateEx` redraws with it in its new place, still open for the next set, with a flash; no other animation (Surath tried folding and gliding and found it too much). Swiping it away from Added offers it under If you have time again. A rest day after a missed session offers to train it instead. Days before `planStart` (the first day the app was opened) are ignored. Nothing is carried into the main plan any more.
- **Recovery:** a compound lift is held back only if a compound for the same muscle was trained yesterday (needs 2 days; `lastTrained` with a kind). Isolation work (flyes, raises, face pulls) never holds the next day's presses: Surath wants chest about three times a week, pressing is his weak point, face pulls count as shoulders but train the rear delts, and a few isolation sets leave far less fatigue than a heavy press. Isolation lifts need 1 day.
- **Lower body once a week:** if two or more leg lifts were logged in the last 5 days, quads, hamstrings and calves wait.
- **Time budget:** 60 minutes (`DAY_MINUTES`) unless another time (45, 75 or 90) is picked for that day (`wk.budget`, `budgetOf`); the next day starts at 60 again. The time and the "Back after a break or illness" switch live in the session card's ⋯ (`.cardmore`, menu `session`), not as tabs or a switch on the card (Surath did not want those). About 11 minutes per compound, 8 per isolation, 6 for abs. Compounds are kept first, then lower `prio`. What does not fit is listed under Left out today.
- Past days show what was logged plus the lifts marked as not done (they still count in that day's ring), and a day that had a session is titled with the session's name, not Logged workout. Future days show only the schedule.
- **Fixing a past day** (⋯ on a past training day since `planStart`, `pastFixes`): Make it a rest day, when one of that week's rest days is still today or later (that rest day becomes a training day and the sessions shift), or Mark as skipped. Both clear the day's logged lifts after a glass alert (`fixPast`), and both have Undo. A day with lifts logged can be fixed even before `planStart` (it was clearly tracked in the app). A past rest day offers It was a training day (the five sessions; picking one makes it a training day and frees its rest day), plus Clear what was logged if lifts are on it. A past training day also offers It was a different session. Empty past rest days and empty days before `planStart` have nothing to fix and show no ⋯. Only a trained training day between the two days blocks a swap; a rest day between has no session to shift.
- Buttons: move the rest day, skip the session, train a different session (saved, with Undo and Back to the plan; the week's other sessions move to cover it; on a rest day it makes the day a training day), add an exercise by hand (does not change the day's type).

## Meal suggestions (`planDay`, shown inside the Eat meal cards)

- Runs on the device, no AI and nothing sent anywhere. It plans every meal after the last one logged that day (a meal not logged yet is still planned, so it is one tap to log), on today and future days, never on past days.
- Suggestions live inside the meal cards under Meals, not in a separate section: each meal not logged yet shows one quiet grey row (`sugBlock`): a small sparkle, the foods with amounts, one line of `kcal · g protein · short tag`, a grey shuffle button for another idea and the food list's round `+` to log it. Keep it low-key: no tinted tile, no coloured macro dots, no filled blue buttons (Surath found those too loud). Logging any food in a meal re-plans the meals after it. A note under the meals says where the day ends with the suggestions (`planNote`). With every meal logged and the day still short, the single-food top-ups (`suggestGap`, `topUps`) appear instead.
- Ideas come from `MEALS` (per slot; `flex` is the food whose amount is tuned, `office` meals are canteen lunches, `usual` marks a standing habit: eggs and whey at breakfast, chicken and rice at dinner) plus meals logged at least twice in the last 60 days (`learnedMeals`, with his real portions).
- Rules are hard filters, never traded off: the daily limits (capped foods are trimmed to the room left or the meal is dropped), fruit only in the snack, no bread at breakfast, and only foods in his list.
- It tries every combination of the remaining meals (12 best ideas per meal, a few ms), sizing each meal in order so what one meal leaves over goes to the next, and keeps the day that lands best: calories close to target, protein at the floor (each gram under weighs about 85 kcal off target) and not over 178 g, fat under the ceiling, one fourth protein source (`FOURTH_PROTEIN`), canteen lunch on `OFFICE_DAYS`, his usual and recent meals first, puddings only when clearly better (cost), a little variety from yesterday.
- `SLOT_SHARE` says how a day is usually spread. "Another idea" moves that meal to its next idea and re-plans the others around it (`ui.planAlt`). The `+` logs all of a meal's foods in that slot.

## Progression rules (`suggest`)

- Double progression. If every set in the last session reached the top of the rep range and there were at least the target number of sets, add the lift's `inc`.
- Otherwise hold the weight. Two sessions in a row under the bottom of the range at the same weight means go one step lighter.
- Gap since the last workout of any kind (not per lift): 5 to 14 days means treat set 1 as a check, 15 days or more means start one step lighter.
- "Back after a break or illness" switch: set 1 one step lighter, add weight from set 2 if easy.
- Single-arm lifts (`single: true`): the left arm leads and the right matches the reps.

## The user's food rules (do not break them)

- Daily limits: **3 whole eggs, 1 whey scoop, 250 g quark, 150 g cooked chicken breast** (raw counts as 0.75), **2 protein puddings per 7 days**.
- Protein 160 g is a floor, fat 70 g (65 on rest days) is a ceiling. Do not push suggestions above about 175 g protein.
- Training day 2,250 kcal, 160 P, 70 F, 235 C. Rest day 2,000 kcal, 160 P, 65 F, 175 C.
- A fourth protein source is needed every day (tuna, chana, dal, soya, turkey). The gap suggester only offers foods that respect these limits.
- Never suggest Harzer Käse, apples, or bread at breakfast. Fruit goes in the afternoon.
- He cooks with a little oil and often under-eats calories and carbs. The fix is carbs and some fat, not more protein.
- Lift names that look alike are different machines and are logged separately: pec deck vs pec fly, leg press vs vertical squat machine. Hammer curls are retired because they injured his elbow.

## Common edits

- **Add a food:** add `F('id','Name','g'|'piece',group,kcal,p,f,c,{step,inc})` to `FOODS`. Unit `'g'` means macros per 100 g. Any other unit means macros per piece or portion.
- **Link a food to a limit:** pass `{cap:'egg'|'whey'|'quark'|'chicken'|'pudding'}`, and `capMul` to convert units.
- **Add or change a lift:** edit its entry in `EX` (rep range `low`/`high`, `sets`, `inc`, `prio`, `ord`, `unit`). Add its id to a session in `TEMPLATES`.
- **Change the week:** edit `DEFAULT_SCHEDULE` for new installs. For the existing user use Settings, or a migration.
- **Add or change a planner meal idea:** edit `MEALS` (and `OFFICE_DAYS` if the office days change).
- **Change the accent colour:** edit `--accent`, `--accent-t` and `--accent-press` in `:root`.

To test cloud sync without touching production, run `api/sync.js` behind a small local Node server with a fake Upstash REST endpoint (it only needs `GET`, `SET` with `EX`, `SCAN`, and the `/pipeline` and `/multi-exec` paths), then drive two browser contexts as two devices. In automated tests, stub `matchMedia` to report reduced motion so sheets and toggles run synchronously. For visual checks, drive the page with Playwright in WebKit and Chromium at 393×852. Headless WebKit does not draw `backdrop-filter` or the incoming page of a view transition, so judge the glass in Chromium or on the phone. When changing the planner or progression, check by hand with `window.__TODAY__` set before load (for example `window.__TODAY__='2026-10-27'`), covering these cases:

1. On Wednesday, rest instead of Thursday: Wednesday is a rest day, Thursday gets Wednesday's session, Friday to Sunday keep theirs, and Eat calls Wednesday a rest day.
2. Missed Monday, on the Tuesday rest day: the card offers Train it today; taking it makes Monday the rest day and Tuesday gets Monday's session.
3. Skipped Wednesday, Friday keeps its own session and shows Wednesday's other lifts under If you have time; lifts done on Thursday are not offered again. With both rest days used, ⋯ only offers Skip.
4. A compound whose muscle had a compound yesterday is held back; pec fly or lateral raises yesterday hold nothing.
5. Legs trained 2 days ago: lower-body lifts wait.
6. All sets at the top of the range adds weight; 12, 12, 5 holds.
7. Add food, edit quantity, remove entry, copy a day, and reload to confirm the data persists.
